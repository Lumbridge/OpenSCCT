## Purpose

The complete replicated interface of the player controller: what the server sends its owner and
what the owner may ask of the server. The player controller is the only actor most client requests
can go through (`model.md` rule 15), so this is where combat, grabs, interactions, gadgets, match
flow, spectating and voice meet the network. Movement and state mirroring have their own files; this
file lists every member, groups them by purpose and states the trust rules that matter for a port.

`PlayerReplicationInfo` (dirty), `PawnClass` (dirty, owner), `StartSpot`. From `PlayerController`:
`GameReplicationInfo`, `m_szGlobalID` (dirty, owner).

## Rules

1. **Audience.** A player controller has a channel only to its owner, so every server-to-client
   member reaches only that player, and only that player can call the client-to-server members.
2. **Running on the receiver.** On the owning client the controller is an autonomous proxy: every
   received function runs, simulated or not. Server-to-client functions called on the listen host's own
   controller run locally on the host (no remote side).
3. **Client-reported damage.** `DamagePawn_C2S(Target, Damage, instigatedBy, HitLocation, Momentum,
   DamageType, PillTag, PercentDamageRefillable)` (reliable, 13 call sites, for example the sticky
   blast with 200 damage) makes the server call `Target.Controller.PawnTakeDamage` with the reported
   values as given, then count merc charge hits and ledge-grab deaths in the player stats. The server
   checks nothing in script. `AskServerToElbowAttack` checks only that the attacker is alive, that the
   target can be elbow-shocked and that the pawns are within 350 uu. `Controller.PawnTakeDamage` is
   itself declared client to server (reliable), so a client can damage its own pawn on the server.
4. **Client-reported positions and directions.** The traversal helpers of `move-protocol.md` rule 14,
   `ServerUpdateActorRotation(A, R)` (server sets the rotation of any actor `A`), and
   `ServerUpdateOrientableRotation(O, iPitch, iYaw)` (server sets `O.iReplicatedPitch/Yaw`, sent by
   `UpdateOrientableRotation` unless `O` is the predicted sticky cam) are applied without checks.
5. **Gadget hand-over.** `AskServerGiveObjectToPawn(gad, pw, NB)` makes the server call
   `TellClientToAddGadgetCharge(gad.GetUniqueIDByClass(), NB)` on the receiving mate's controller; that
   client walks its gadget list for the matching id, shows "NB name received" for 3 s and adds one
   charge.
6. **Match start.** `launchMatchNow` (simulated, reliable, to owner) sets
   `GameReplicationInfo.bMatchLaunchingNow` and `bMatchLaunching` on the client copy of the GRI;
   `StartMatchOnServer` (client to server) sets `bMatchHasBegun` and calls `Level.Game.StartMatch()`.
7. **ForceRotateTo(Rot, Side, Step)** (reliable, server to owner) stores `FRTarget`, `FRSide`,
   `FRStep` for the client's forced turn; the rotator loses its low 8 bits.
8. **Render capabilities** (Reloaded/Enhanced): `RequestRenderCaps(Token, Key)` on the server sends
   `ClientSendRenderCaps` (reliable, simulated); the client answers
   `ServerSetRenderCaps(NativeRenderCaps(Token, Key))`, and the server stores it natively. Both natives
   are `Reloaded.Core.dll` thunks.
9. **Native RPC bodies.** `SetClientShouldShowMenu` (native 1376) and `ForceLeaveMatch` (native 1836)
   are server-to-client RPCs with native bodies; `SetShouldShowMenu` calls the first only on the
   server.
10. **Controller engine members.** `ClientSetLocation`, `ClientSetRotation`, `ClientDying`,
    `ClientGameEnded` use the condition `RemoteRole == ROLE_AutonomousProxy`, so on a listen host they
    run locally for the host's own player. `PlayerController` keeps the stock UE2 client messaging,
    sound, travel and voice calls; `ClientHearSound`, `ClientValidate`, `ClientTravel` and
    `ServerValidationResponse` have native bodies.
11. **Two ClientShake functions.** `PlayerController.ClientShake(Vector, Vector, Vector, float)` is
    private and unreliable; `SPlayerController.ClientShake(strenght, speed, FadeOut, bTilt, bShake,
    bRumble)` is a separate reliable simulated function. SCCT code calls the second.

## Network

Everything here is on the player controller channel: server and owning client only. Reliability per
member is in the tables ("R" reliable, "U" unreliable). Unreliable members are the movement messages,
the corrections, the proxy updates, `UpdatePositionForServer`, `UpdateDesiredRotation`,
`ServerUpdateOrientableRotation`, `CheckPlayersOnClient`, `ScriptEventToClient`,
`SetHudPerturbation`, `AddGPOOnHud`, `RemoveGPOFromHud`, `AddMessageOnHud`, plus the engine
`ClientHearSound`, `ClientPlaySound`, `SetFOVAngle`, `ClientFlash`, the engine `ClientShake`, `Say`,
`TeamSay`, `ServerSetHandedness`, `ServerDrive`, `ServerUpdatePing`, `ServerViewSelf`,
`SendVoiceMessage`, `SetPawnClass`.

## Edge cases

- Unreliable HUD calls (`AddGPOOnHud`, `RemoveGPOFromHud`, `AddMessageOnHud`) can be lost; an add
  without its remove leaves a stale HUD marker until the next add or remove.
- `MyDesiredRotation` replicates only in the first bunch; afterwards the client owns it and the
  server learns it through `UpdateDesiredRotation`.
- Several client-to-server calls take actor references (`DestroyGPO(gpo, Damage, Type)`,
  `ServerUpdateActorRotation(A, R)`, `TellServerToFallAttack(Other)`); the port must resolve them by
  network id exactly like the original and, to stay faithful, must not add checks the original lacks
  (record any anti-cheat check as a separate, switchable rule).
